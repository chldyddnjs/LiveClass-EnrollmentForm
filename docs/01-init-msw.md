### 문서 개요

본 문서는 다단계 수강 신청 폼 구현 과정에서 내린 기술적 의사결정과 그 근거를 기록합니다. 각 커밋 단계별로 무엇을 왜 선택했는지를 중심으로 작성됩니다.

---

### 1. 배경 및 목적

수강 신청 폼은 강의 목록 조회와 신청 제출이라는 두 개의 API에 의존합니다. 백엔드 없이 프론트엔드 개발을 독립적으로 진행하려면 API 의존성을 로컬에서 해소할 Mock 환경이 선행되어야 합니다. 이 커밋은 이후 모든 개발의 기반이 되는 환경 구성을 목적으로 합니다.

---

### 2. 기술 스택 선택 근거

### 2-1. 빌드 도구: Vite

CRA(Create React App)는 현재 유지보수가 중단된 상태입니다. Vite는 ESM 기반 HMR로 개발 서버 기동 속도가 빠르고, TypeScript를 별도 설정 없이 지원합니다. 과제 규모에서 React를 권장하므로 Vite를 선택했습니다.

### 2-2. 폼 상태 관리: React Hook Form

폼 라이브러리 후보는 세 가지였습니다.

| 항목 | React Hook Form | Formik | 직접 구현 |
| --- | --- | --- | --- |
| 렌더링 방식 | Uncontrolled (ref 기반) | Controlled | Controlled |
| 리렌더 최소화 | 우수 | 보통 | 구현에 따라 다름 |
| 스키마 연동 | Zod, Yup 등 | Yup 중심 | 직접 연결 필요 |
| 학습 비용 | 낮음 | 낮음 | 없음 |

참가자 명단처럼 동적으로 필드가 추가되는 경우 Controlled 방식은 입력마다 전체 리렌더를 유발합니다. React Hook Form의 `useFieldArray`는 이 문제를 ref 기반으로 해결하므로 선택했습니다.

### 2-3. 스키마 검증: Zod

Zod는 스키마 정의와 TypeScript 타입 추론을 단일 소스에서 처리합니다. `z.infer<typeof schema>`로 타입을 별도 선언 없이 뽑아낼 수 있어 타입 정의와 검증 로직이 이중으로 관리되는 문제를 방지합니다. `discriminatedUnion`으로 개인/단체 신청 타입 분기를 명시적으로 표현할 수 있는 점도 이 과제에 적합했습니다.

### 2-4. 서버 상태 관리: TanStack Query

강의 목록 조회는 로딩 상태, 에러 상태, 캐싱, 리패치를 모두 처리해야 합니다. 이를 `useState` + `useEffect`로 직접 구현하면 코드량이 늘고 엣지 케이스(언마운트 후 setState 등)가 생깁니다. TanStack Query는 이 패턴을 선언적으로 처리하며, `staleTime` 설정으로 불필요한 중복 요청을 방지합니다.

### 2-5. Mock 환경: MSW (Mock Service Worker)

- **MSW**: Service Worker 레벨에서 실제 네트워크 요청을 인터셉트하므로 `fetch` 호출 코드를 전혀 바꾸지 않아도 됩니다. 핸들러에서 에러 코드, 응답 지연, 상태 변화(정원 감소)를 자유롭게 시뮬레이션할 수 있습니다.

MSW는 `import.meta.env.DEV` 조건 아래에서만 활성화되므로 프로덕션 빌드에 영향을 주지 않습니다.

---

### 3. 타입 설계 원칙

신청 유형(개인/단체)에 따라 필요한 필드가 완전히 달라집니다. `type` 필드를 리터럴 타입으로 두고 `discriminated union`으로 분기하면, TypeScript가 `type === "group"` 분기 안에서 `group` 필드의 존재를 자동으로 보장합니다. `any`나 옵셔널 유니온으로 처리할 경우 런타임에서만 발견되는 타입 오류를 컴파일 타임에 잡을 수 있습니다.

---

### 4. Mock 핸들러 설계 결정

실제 비즈니스 규칙을 Mock 단계에서도 반영했습니다.

- **정원 초과 시뮬레이션**: `currentEnrollment`를 메모리에서 누적해 실제 정원 계산과 동일하게 동작합니다.
- **중복 신청 감지**: `Set<string>`으로 세션 내 신청 이력을 추적합니다. 브라우저 새로고침 시 초기화되는 것은 Mock의 한계로 인정합니다.
- **응답 지연 600ms**: 즉시 응답 시 로딩 UI가 너무 빠르게 사라져 테스트가 어렵습니다. 실제 네트워크 환경과 유사한 600ms를 고정값으로 설정했습니다.
